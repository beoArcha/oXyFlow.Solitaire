## Resolved by the user (2026-11-19) — card graphics

### D-06 Card graphics delivery — DECIDED (final)

Decided after spike X-01 (report: [`spikes/x-01-card-font.md`](spikes/x-01-card-font.md), §5 and §6) at
checkpoint F-02. It makes T-16 final and amends R-03 ("delivered as fonts"). Consequence the owner
accepts: a player sees the custom artwork only after installing the oXySol card font and switching Font
mode on; everyone else gets the Unicode or ASCII rendering. The game never installs a font.

1. **Delivery.** oXySol ships its own complete monospace font with the card glyphs in the BMP Private Use
   Area.
   - When the font is installed, the game can switch the classic Windows console to it itself with
     `SetCurrentConsoleFontEx`. This is an option in Settings and part of the existing Font render mode.
   - Without the font the game uses today's Unicode and ASCII glyphs.
   - Font mode stays opt-in (T-16): in general the font cannot be detected. On the classic console the
     game can check whether the font is registered.
2. **Base font and licence.** The base is Cascadia Mono (SIL OFL 1.1).
   - The derivative font is published with the game under a different family name (working name
     `oXySol Mono`), with the OFL text and the copyright notices kept in the font and in the archives, and
     with no Reserved Font Name of the base.
   - R-10 stands: the patched font keeps the licence of its base. The card artwork sources stay MIT.
   - Gap: `THIRD-PARTY-LICENSES.md` comes from `cargo-about` (T-31), which lists crates and not fonts. The
     font licence is therefore added to the release archives by hand, tracked as O-35.
3. **Build tool.** Python with fontTools and skia-pathops, run from `cargo xtask fonts`.
   - Python is needed only to regenerate the font. The built font file is committed, so an ordinary
     `cargo build` needs no Python. Versions are pinned in a requirements file (P5-01).
4. **Windows Terminal** is a supported target from documentation. The game shows a hint on how to set
   the font face (or face list) in the profile. A test on a real machine is a follow-up, O-34, for when the
   owner installs Windows Terminal.
5. **Scope.**
   - Single-cell glyphs: suits, court emblems and back tiles.
   - Small mosaic decorations (2 × 2 cells) at larger cell sizes, about 10 × 24 px and up.
   - No full-card illustrations.
   - Code points U+E6BC–U+E6FF only (68 code points). No plane 16: it renders as squares in the classic
     console (verified in X-01).

The glyph box (Cascadia Mono cell: UPM 2048, advance 1200, ascent 1900, descent 480, line gap 0), the
code point table and the artwork rules are in the style guide on the shared card of M-19…M-24 in
`docs/task_list/micro.md`.

## Technical decisions — owner: architect

| ID | Decision | Rationale |
|---|---|---|
| T-01 | Workspace: `oxysol-core` (engine plus four games as modules), `oxysol-tui`, root package `oxysol` (lib + bin), tooling crate `xtask`. No separate `games` crate. | Cargo enforces the engine/TUI boundary at compile time. A games crate adds nothing over `pub(crate)` modules. |
| T-02 | **Revised by R-19.** SQLite through `rusqlite` with feature `bundled` (compiled from source, no system library). One file `oxysol.db` in the data directory; schema version in `PRAGMA user_version` with forward-only migrations in code; every write in a transaction. Structured values (`Settings`, `SessionRecord`) are stored as JSON text (`serde_json`) in columns. | Game history and seeds need queries; the bundled build works on all CI runners, musl included (`musl-tools`). Transactions replace temp-file-and-rename. |
| T-03 | A saved game is variant + seed + move log + history cursor + elapsed time. State is rebuilt by replaying the log; the same mechanism implements undo, redo and resume. | One mechanism instead of three, no inverse moves, tiny files. Cost: a change to rules or shuffling invalidates old saves — guarded by golden-deal tests and the `format` field. |
| T-04 | Own SplitMix64 generator and Fisher–Yates shuffle in `core::rng`. | A seed must give the same deal on every platform and app version (needed by T-03). About 30 lines, no dependency. |
| T-05 | A shared command vocabulary (`Move`, `PileRef`) and a small `Game` trait; rules of each game in its own module. | The TUI drives all games with one interaction code path while mechanics stay separate. |
| T-06 | Own minimal localization: TOML files `locales/<lang>/<area>.toml`, embedded, string keys, fallback to `en-US`. Messages are worded to avoid plural forms. | A few dozen strings do not justify a framework. Per-area files avoid merge conflicts. |
| T-07 | Styles are data folders: `assets/cards/fronts/<style>/`, `assets/cards/backs/<style>/`, `assets/audio/<style>/`, each with a `style.toml` manifest. A build script embeds every folder it finds. | Adding a style is adding a folder; no code changes, no shared file to conflict on. |
| T-08 | Tooling as `cargo xtask`, not shell scripts. The custom checker covers only project rules (LOC, nesting, comments in functions, error policy); everything else is Clippy and compiler lints. | One tooling codebase for three systems. |
| T-09 | Error types via `thiserror`, no `anyhow`. CRITICAL = `tracing::error!` with target `oxysol::critical`. | Precise types at every boundary; `tracing` has no CRITICAL level. |
| T-10 | Windows: default console subsystem, no `AttachConsole`/`AllocConsole`, no `windows_subsystem`. | A console app started from a terminal uses that console; started by double-click it gets its own window from the OS. No code, no `unsafe`. Verified manually in U-03. Exception (O-05): after an error exit, a process whose console it alone owns (a double-click) waits for Enter before the window closes, via `console::owns_window` (one `GetConsoleProcessList` call). |
| T-11 | Minimum grid 100 × 30 cells; below that a notice screen. | 854 × 480 px at an 8 × 16 px cell is 106 × 30; 100 columns leaves margin for other fonts. |
| T-12 | E2E tests run in-process: `App` + `TestBackend` + real `SqliteStorage` in a temp dir, plus a binary smoke test. | Pseudo-terminal tests differ per OS and are flaky. |
| T-13 | Scaling means card size, spacing and margins in cells. | The user's terminal controls the font size. |
| T-14 | Clock and seed generation live outside the engine. | The engine stays deterministic and free of I/O. |
| T-15 | Dependencies are added only by phase tasks on the Claude lane. Micro tasks never touch `Cargo.toml` or `Cargo.lock`. | No merge conflicts, controlled dependency list. |
| T-16 | **Graphics (final, D-06, after X-01):** SVG sources are compiled by `cargo xtask fonts` (Python, fontTools, skia-pathops) into one complete monospace font, `oXySol Mono`, a patched copy of Cascadia Mono (SIL OFL 1.1) under a different family name; the card glyphs sit in the BMP Private Use Area, code points **U+E6BC–U+E6FF only (68, no plane 16)**, assigned in `assets/cards/codepoints.toml` (an assigned code point never changes). The glyph box is the Cascadia Mono cell: UPM 2048, advance 1200, ascent 1900, descent 480. The built font is committed under `assets/fonts/`, so `cargo build` needs no Python. Three render modes: Font, Unicode, ASCII; the default is Unicode. Font mode is opt-in: the player turns it on in a graphics-check screen, and on the classic Windows console the game can also switch the console to the font itself (`SetCurrentConsoleFontEx`, an option in Settings) when the font is registered. Windows Terminal is supported from documentation with an in-game hint on the font face. Scope: single-cell glyphs (suits, court emblems, back tiles) and small 2 × 2 mosaic decorations at larger cell sizes; no full-card illustrations. Raster protocols (Kitty, Sixel, iTerm2) are post-MVP and would use the same SVGs. | The classic console has one font and no fallback list (X-01: a glyph-only font turned all text into squares, a complete font rendered everything), so a complete patched font is the only way to reach it. Plane 16 failed to render, so the BMP range found free of Nerd Fonts, Font Awesome 6 and the Segoe icon fonts is the whole budget. Fonts stay sharp at any size and work over SSH because rendering happens on the player's machine. Python is the only tool that builds and patches fonts with little code; committing the output keeps it off the normal build path. |
| T-17 | **Audio:** `.mid` files per sound style, parsed with `midly`, played by a small built-in polyphonic synthesizer (oscillators and envelopes; timbres defined in `style.toml`), output through `cpal`, behind cargo feature `audio`. No audio device, or an SSH session, means audio is off and the game is unaffected. No SoundFont in MVP. The TUI `Audio` trait keeps cues and music separate so an external music source can replace music later. | A SoundFont adds megabytes and licensing review; a built-in synth keeps sound styles small, text-defined and authorable by agents. The sound is deliberately simple. |
| T-18 | **Revised 2026-11-15 (owner).** Linux releases ship only the static musl builds, and those are built with `--no-default-features`: Linux builds are silent and have no glibc build with audio. Linux CI runners install `libasound2-dev` so that the default `audio` feature still builds and is tested there. | Servers reached over SSH often lack ALSA; a binary linked to it would not start there. A static musl build cannot link ALSA at all, so Linux releases ship without sound. |
| T-19 | **Revised by R-16, R-17.** `pr.yml` (Linux) runs `cargo xtask check --pr <base>`: fmt, Clippy, lint, the architecture and E2E suites, and unit/integration tests of affected packages only. `main.yml` runs `cargo xtask check` on Linux, Windows and macOS, then a `promote` job fast-forwards `release` and dispatches `release.yml`. `release.yml` (push to `release`, `workflow_dispatch`) runs the full check on three systems, builds, tags, publishes the GitHub Release and deploys GitHub Pages. | The repository is public, so Actions minutes on standard runners are free and PRs can afford the E2E and architecture suites. |
| T-21 | **Revised 2026-11-19 (owner), R-23.** Release versions: `metadata.toml` holds `major.minor.0`, set by hand when a plan phase closes (R-23). The effective version is `major.minor.P`, where `P` is the number of first-parent commits on `HEAD` since the commit that last changed the `version` line of `metadata.toml` (`git log -1 --first-parent -G '^version *=' -- metadata.toml`, then `git rev-list --count --first-parent <base>..HEAD`), added to the patch of that line. Squash merges give one commit per merge, so every merge to `main` raises the patch by 1, and no bot commit is needed. `cargo xtask version` prints the effective version and `--tag` prints `v<effective>`; `build.rs` computes the same value through the same code (`xtask/src/version_scheme.rs`) and exports it as `OXYSOL_VERSION`, which `--version`, the main menu label and the Windows file version use. Without usable git history (a source archive, a shallow clone) the build falls back to `<metadata version>+src` and never fails. A `release.yml` run publishes the tag `v<effective>` as a pre-release; with `stable: true` it publishes the same tag as a full release. A tag that exists at another commit fails the run; at the same commit with a release it publishes nothing, except that `stable: true` promotes an existing pre-release to a full release. | `main` is protected and agents never push to it, so the patch is derived from git, not stored. Every merge is one visible version step, and a stable release stays a deliberate act. |
| T-22 | Affected packages: `cargo xtask affected --base <ref>` maps changed paths to workspace packages and adds reverse dependents (`oxysol-core` → `oxysol-tui` → `oxysol`; `xtask` alone). | T-24 | Logging: `tracing` to `oxysol.log`, default level `info`, `OXYSOL_LOG` overrides. Every deal (variant, seed), resume, outcome and storage error is logged; moves at `debug`. | "Full" text logs that reproduce a session together with the seed. |

| T-26 | Application icon (O-09): sources are vector only — `assets/icon/oxysol.svg` (48 px and up) and hand-simplified `oxysol-32.svg` (up to 40 px) and `oxysol-16.svg` (up to 24 px). `cargo xtask icon` renders them with `resvg` (no text, fonts or raster-image features) to 16, 20, 24, 32, 40, 48, 64, 96, 128 and 256 px and writes `assets/icon/generated/oxysol.ico` (PNG-compressed entries) and `oxysol-256.png`; the generated files are committed. `cargo xtask icon --check` fails when they are stale (pixel comparison with a tolerance of 2 per channel) and runs in the full `cargo xtask check`. Small sizes are drawn by hand because a scaled-down detailed icon turns to mush at 16 px. |
| T-27 | Copying a seed (P4-04): a `Clipboard` trait in the TUI like `Audio`, implemented in `oxysol` with the `arboard` crate (default features off: text only, X11 through pure-Rust `x11rb`, no native library to link) and the OSC 52 terminal escape as the fallback when the native clipboard fails or the session is remote. The seed is always shown as text, and the result of a copy is announced. | `arboard` builds for Windows, macOS and static musl Linux without system libraries; over SSH the server's clipboard is useless, while OSC 52 reaches the player's terminal. OSC 52 gives no acknowledgement, so the text stays visible for manual selection. |
| T-28 | Opening in a new console window (O-15): `--new-window` (also `-n`) relaunches the executable with the same arguments minus that flag and exits with code 0 at once; the window closes when the game exits and a startup error still pauses for Enter (O-05), because the new console is owned by the game. The parent opens only the log (one `info` line), never the database. Commands are built by pure functions in `src/new_window.rs`. Windows: the executable itself with `creation_flags(CREATE_NEW_CONSOLE)` (`0x10`), no `unsafe`; working directory and environment are inherited. Linux: `$TERMINAL -e`, `x-terminal-emulator -e`, `gnome-terminal --`, `konsole -e`, `xterm -e`, the first that starts. macOS: `osascript -e 'tell application "Terminal" to do script "<line>"'` with a shell line `cd <cwd> && OXYSOL_HOME=… exec <exe> <args>`, every word single-quoted for the shell and then escaped for AppleScript (a fresh shell inherits neither directory nor variables, so both are passed; whether the window closes at exit follows the Terminal profile). If nothing starts, the error names what was tried and the exit code is 2. `cli.help` is the one text of the options: `--help` prints it and the "Command line" tab of the Help window shows it. | A double-click already gives a window of its own; this gives the same from a console and from shortcuts. Only Windows has a documented single call with no external program; on Linux and macOS there is no standard terminal, hence the ordered list. Only the Windows path was run by hand; the Linux and macOS commands are covered by unit tests of their construction. |
| T-29 | Solver for winnable deals (P2-08): `crate::solver`, `solve(variant, seed, SolveBudget) -> Verdict { Winnable { moves }, Unwinnable, Unknown }`. Budget = a count of generated positions (core stays clock-free). Per game a compact model built from `piles()`, searched with a visited set of 128-bit canonical keys (columns and cells unordered). Klondike (draw 1 and 3): depth-first, safe foundation moves at once, a talon card is played together with the stock draws that bring it to the waste top, foundation-to-column moves kept for completeness. FreeCell: greedy best-first on a work-left estimate (cards home, cards burying the next foundation card, blockers, full cells), safe foundation moves at once. Spider: depth-first with moves ordered by effect (complete a run, join a suit, turn a card over, deal last); with 2 and 4 suits mostly `Unknown`. Pyramid: depth-first, lone kings removed at once, a cheap partner-count test proves dead positions; Classic is mostly proven unwinnable. Winning lines are replayed on a fresh deal and ended by the engine's `forced_finish` where a model predicts a certain win; `Unwinnable` is only reported after exhausting the space. The solver knows the stock and the face-down cards, so "winnable" means thoroughly solvable. Default budgets (positions): Klondike 100,000, FreeCell 100,000, Spider 60,000, Pyramid 500,000. Measured on 50 seeds (0-49) per variant, release build, this machine (winnable / unwinnable / unknown, average and slowest time): Klondike draw 1 76 / 2 / 22 %, 111 ms, 564 ms; Klondike draw 3 70 / 6 / 24 %, 223 ms, 1051 ms; Spider 1 suit 94 / 0 / 6 %, 39 ms, 500 ms; Spider 2 suits 14 / 0 / 86 %, 312 ms, 533 ms; Spider 4 suits 2 / 0 / 98 %, 251 ms, 405 ms; FreeCell 98 / 0 / 2 %, 11 ms, 210 ms; Pyramid Relaxed 70 / 8 / 22 %, 117 ms, 427 ms; Pyramid Classic 8 / 90 / 2 %, 102 ms, 475 ms. | The offered deals of P3-20 must be proven winnable, and a game must never be called unwinnable on a guess. Models keep the search fast (up to about 1.5 million positions per second for Pyramid, 150,000 to 200,000 for Klondike and Spider); the engine stays the judge through the replay, and tests compare every model with the engine move by move. |
| T-30 | Winnable deals only (P3-20): the TUI owns the search state and asks a `Solver` trait (`submit`/`cancel`/`poll`); the binary wires one worker thread, so the interface never waits for the solver. A search queues 40 seeds at once (`SEED_CAP`) and takes the first proven winnable one; at the cap the player may play the first undecided seed as "unknown", keep searching or cancel. Seeds the player chose (typed, replay, resume) are never replaced, only checked in the background and reported in the game information.
